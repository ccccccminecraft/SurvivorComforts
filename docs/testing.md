# テスト

ゲームの中で、この MOD の自動のテストを動かす仕組みです（2026-11-01 に土台を作成。全体の点検の R6-1）。

- [README に戻る](../README.md) ／ 詳しい開発の手順は [dev-guide.md](dev-guide.md)

## 仕組み

- テストは、配る MOD とは別の、**テスト用の MOD**（MOD ID `SurvivorComfortsTests`）に入れる。場所はリポジトリの `mod-tests/SurvivorComfortsTests/`
  - ワークショップには上げない。`tools\deploy.ps1` もコピーしない。遊ぶ人のゲームには入らない
  - `mod.info` で本体の MOD（`SurvivorComforts`）を前提にしている（`require`）
- テストを動かす画面は、ゲームのデバッグメニュー →「開発」→「ユニットテスト」。ゲーム本体のテスト（時間のかかる動作）のタブの横に、「Survivor Comforts」のタブを足している
  - 「全部実行」「止める」と、テストごとの「実行」と結果（成功・失敗・かかった時間）が並ぶ
  - デバッグメニューの「スクリプトマネージャー」は、アイテムやレシピのスクリプトを見る画面で、テストとは関係ない
- 結果は `console.txt` にも出る。`[SurvivorComfortsTests]` で検索する
  ```
  [SurvivorComfortsTests] PASS Search: parse splits on spaces (0 ms)
  [SurvivorComfortsTests] FAIL Search: ... : expected "a", got "b"
  [SurvivorComfortsTests] SKIP MP F09: ... : multiplayer only
  [SurvivorComfortsTests] done: 3 passed, 0 failed, 1 skipped
  ```
- シングルプレイでしか確かめられないテストはマルチプレイで、マルチプレイでしか確かめられないテスト（名前が `MP ` で始まる、`Tests_Multiplayer.lua`）はシングルプレイで「スキップ」になる。失敗にも成功にも数えない（2026-11-07）
- テストは、自分でデバッグメニューの「ユニットテスト」から始める。ゲームを始めても自動では走らない（一度は自動で走らせる作りにしたが、ゲームに入るたびに画面が開いたり閉じたりして驚くので、やめた。2026-11-01）

## 動かし方

テスト用の MOD もコピーして有効にするには、起動のスクリプトに `-Test` を付ける。

```
powershell -File tools\test_debug.ps1 -Test
```

- シングルプレイのデバッグモードで起動する。「ソロ」で新しいゲームを始め、デバッグメニュー →「開発」→「ユニットテスト」→「Survivor Comforts」の「全部実行」で走らせる
- マルチプレイのテスト（サーバーの答えを確かめるもの）は、`tools\test_server.ps1 -Debug -Test` で起動する。サーバーの MOD の一覧にもテスト用の MOD を足す（マルチプレイでは、サーバーの一覧にない MOD は読み込まれないため）。デバッグモードでは管理者のアカウントで入る（[dev-guide.md の「デバッグモードで試す」](dev-guide.md#デバッグモードで試す)）
  - マルチプレイでも「全部実行」でよい。シングル用のテストはスキップになる。2人で入ると、ほかの人のスキル（F15）や一覧（F09）も確かめる
- `-Test` を付けないときは、前にコピーしたテスト用の MOD を消して、本体の MOD だけで起動する
- `tools\check.ps1` は、テスト用の MOD の Lua も構文をチェックする

## テストの書き方

テストは `mod-tests/SurvivorComfortsTests/42/media/lua/client/SurvivorComfortsTests/` に、対象ごとのファイル（例：`Tests_Search.lua`）で置く。

```lua
require "SurvivorComfortsTests/Runner"
local T = SurvivorComfortsTests

-- すぐに終わるテスト。確かめる処理が失敗すると、そこで止まって FAIL になる
T.add("Search: parse splits on spaces", function(t)
    local words = SurvivorComforts.search.parse("Saw  logs")
    t:equal(#words, 2)
    t:equal(words[1], "saw")
end)

-- 待つ必要があるテスト（サーバーの答えなど）。check が true を返したら then を実行して PASS、
-- timeout（ミリ秒）を過ぎたら FAIL
T.add("F15: the server answers", function(t)
    -- 頼む処理
    t:waitFor(function() return received ~= nil end, 5000, function()
        t:equal(received.username, "admin")
    end)
end)
```

- 確かめる処理：`t:equal(実際の値, 期待する値, 説明)`、`t:ok(値, 説明)`（値が false か nil なら失敗）、`t:fail(説明)`
- このゲームでは確かめられないテストは、最初に `if isClient() then return t:skip("single player only") end` のように抜ける（スキップ）
- 確かめる処理は、失敗してもテストを止めない（失敗を覚えておき、テストの最後に FAIL にする）。どれも、合っていれば true、違えば false を返すので、前提が崩れたら `if not t:ok(x, "...") then return end` で抜ける
- テストの中で、わざと Lua のエラーを起こさない。デバッグモードのゲームは、`pcall` で受け止めたエラーでも止まって、エラーの画面（`Runner.lua` の `onTick` などが並ぶ）を出すため。テストの確かめる処理も、エラーを使わない作りにしている（2026-11-01）
- 名前は「対象: 内容」（例：`Search: parse splits on spaces`）。画面とログで、名前の順に並ぶ
- テストは1つずつ順に、1フレームに1つずつ実行する。前のテストの状態に頼らない
- ゲームの世界を変えるテスト（アイテムを出すなど）は、テスト用のセーブ（`%USERPROFILE%\PZTest`）でだけ動かす。後片付け（出したアイテムを消す）もテストの中でする

残りのテスト（下の表で「まだ」のもの。C のマルチプレイと、B のいくつか）は、後で実装する（2026-11-01 決定。先に導入を進める）。

- A と B の一部は、今は各ファイルの中だけの関数（`local`）なので、テストから呼べるように出し方を変える必要がある（例：F09 の「○分前」、F04 の時間の表示）。必要なものは、下の「テストから呼べるようにする関数」にまとめた
- 見た目（位置のずれ、色の見え方、文字が切れないか）は、テストでは確かめられない。今までどおり、機能ごとの確認項目で目で確かめる

## 機能ごとのテスト（洗い出し）

各機能と共通の処理で、自動で確かめたいことを洗い出した（2026-11-01）。テストの名前は「対象: 内容」の英語で付ける予定（ゲームの Lua に日本語を書けないため）。

- 段階：A（計算だけ）／B（シングルプレイの世界。デバッグモードのゲーム）／C（マルチプレイ。テスト用のサーバー）
- 状況：✅ 済み ／ ⬜ まだ
- シングルプレイでは、サーバー側の Lua（`server/`）も同じゲームの中で動く（`isClient()` も `isServer()` も false）。そのため、F06 のサーバーの処理と回数の制限は、B で直接確かめられる。F09 と F15 のサーバー側は、本物のサーバーでしか動かない（`isServer()` のときだけ）ので C で確かめる
