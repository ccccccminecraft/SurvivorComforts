### 詳しい調査（2026-10-30）

起きていること：日本語入力（IME）をONにすると、ゲームの操作が効かなくなる。打った文字は画面の左上に出て、Enterで確定してから英語に戻すと操作できるようになる。

ゲーム本体の仕組み（`projectzomboid.jar` で確認）：
- ゲームの窓とキー入力は LWJGL の GLFW で動いている。同梱の GLFW は **3.5.0（開発版）で、日本語入力の機能をすでに持っている**
  - IMEのON/OFFを切り替える設定（`glfwSetInputMode` の `GLFW_IME`）
  - 変換中の文字を受け取る（`glfwSetPreeditCallback`）、変換中の文字を出す位置を決める（`glfwSetPreeditCursorRectangle`）、IMEの状態の変化を受け取る（`glfwSetIMEStatusCallback`）
  - GLFW の中で Windows の IME の関数（`ImmGetCompositionStringW`、`ImmSetCompositionWindow` など）を使っている
- **ゲーム本体はこれらを1つも使っていない**（「実装はされているが使われていない」という話は、これのこと）。そのため Windows の標準の動きになり、変換中の文字は画面の左上に出て、IMEがONの間はキーがIMEに取られてゲームの操作が効かない
- 確定した文字は、GLFW の文字入力（`glfwSetCharCallback`）→ `Keyboard.addCharEvent(char)` → 文字入力欄（`UITextBox2.putCharacter`）と渡る。文字の種類で弾く処理はないので、確定した日本語は入力欄に入る見込み（ゲームでは未確認）

公式のMOD機能（Lua）でできるか：**できない**
- Lua から呼べる Java の機能は、ゲームが公開したものだけ。GLFW の関数（IMEのON/OFF、変換中の文字）は公開されていない
- 公開されている `Keyboard` はキーの番号表と、キーが押されているかの確認だけで、IMEに触る機能はない
- Lua のグローバル関数が GLFW を使っているのは、キーの番号の変換（`KeyCodes.toGlfwKey`）だけ
- ゲームには JNA（`jnidispatch.dll`。Java から Windows の関数を直接呼ぶ仕組み）も入っているが、Lua からは使えない

ZombieBuddy（Java のMOD）を使えばできるか：**できる見込み**
- Java の処理を足せるので、ゲームに同梱の GLFW の IME の機能をそのまま呼べる。例えば「文字入力欄を選んでいる間だけIMEをON、それ以外はOFF」「変換中の文字を入力欄の位置に出す」
- ただし、[5章（研究メモ）](../research.md)の制約がそのまま当てはまる
  - 遊ぶ人全員が、自分のPCに ZombieBuddy を入れる必要がある（Workshop の購読だけでは足りない）
  - Java のMODは PC 全体に無制限に触れる。配る相手に信頼してもらう必要がある
  - ゲームの中身に直接手を入れるので、アップデートで壊れやすい
- 一方で、IMEはクライアントだけの話なので、サーバーにMODを入れる必要はない

MODを使わない回避策：
- Windows の設定 →「時刻と言語」→「入力」→「キーボードの詳細設定」→「アプリ ウィンドウごとに異なる入力方式を設定する」をONにする。ゲームの窓は英語入力のままになり、チャットのときだけ IME をONにすればよい（変換中の文字が左上に出るのは変わらない）

結論（2026-10-30 に決定）：
- 日本語入力は、Lua だけの SurvivorComforts には入れられない。ZombieBuddy を前提にした別のMODとして扱い、**SurvivorComforts には同梱しない**のがよい
- 状況を「⏸️ 見送り」にし、[features.md](../features.md) の「実装しない機能」に移した。日本語入力が必要な人は、ZombieBuddy を使った別のMOD（身内で作ったもの）を使う
